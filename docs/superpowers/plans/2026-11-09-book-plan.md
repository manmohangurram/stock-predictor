# Book-aware plan calls — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The model sees the whole book and a hard spending cap on every call, and once per poll may propose up to three moves that are stored, approved or rejected as one plan.

**Architecture:** Two changes to what the prompt knows (a cap line and a book block), then one new call (`plan_v1`) that returns 0–3 moves, validated leg-by-leg and then as a whole, stored as one `signals` group via `plan_id`, and approved/rejected atomically through the existing decision endpoints.

**Tech Stack:** Rust (axum, sqlx/SQLite, tokio), plain TypeScript front end built by Vite, `vitest`.

**Spec:** `docs/superpowers/specs/2026-11-09-book-plan-design.md`

## Global Constraints

- No test may hit the network. Fixtures only.
- `api_calls` and `cash_ledger` are append-only.
- Environment stays four variables: `BIND`, `DB_PATH`, `PUBLIC_URL`, `SECRET_KEY`.
- Validator refuses, never repairs: a plan that fails any check is refused whole, with reasons stored.
- Two pots never share capital; the long-term book is stocks and funds, short-term only stocks.
- Gates: `cargo test` green, `cargo clippy --all-targets` warning-free, `cd web && npx vitest run && npm run build` green.
- Copy rule: the cap sentence is *exactly* `You may spend at most {amount} {currency} in this purse.` followed by `A buy costing more than that is refused, not shrunk.`

## Review Focus

- A purse with zero available cash: the prompt must say `at most 0.00`, and a buy must not be proposed as affordable.
- A book with 30 holdings: the block must truncate with `+N more` and never exceed 13 lines, so the prompt cannot grow without bound.
- A plan selling an instrument that is not held: refused whole, with `NotHeld` in the stored reasons.
- A plan buying and selling the same symbol: refused whole (`DuplicateSymbol`), because the net effect is unreadable to the person approving it.
- A plan approved twice (double click): the second call must answer `400 already approved`, not post the legs twice.
