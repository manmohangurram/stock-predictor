# Bars in tiers — plan

Status: agreed 2026-11-25. Spec: `docs/superpowers/specs/2026-11-25-bar-tiers-design.md`.

Four slices, one stack. Each slice is independently green; the bottom PR targets `main` and every
PR above it targets the branch below. The conversion of existing rows ships **with** the reader
that understands them, never before it.

---

## Slice 1 — schema and the reader that understands buckets

Branch `feat/bar-tiers-schema`.

- Migration `0033_bars_resolution.sql`: `ALTER TABLE bars ADD COLUMN resolution TEXT NOT NULL
  DEFAULT 'daily'`, plus an index on `(instrument_id, resolution, ts)`.
- `rules.Bucket` — `EndsOn`, `Sessions`, `Mean`, `High`, `Low`.
- `rules.ComputeIndicatorsFrom(daily []models.Bar, buckets []Bucket)`: SMA50/RSI14/ATR14 from the
  daily rows, SMA200 and High52/Low52 by walking daily then buckets, weighted by session count.
  `ComputeIndicators(bars)` delegates with no buckets, so every existing caller and test is
  unchanged.
- `store.DailyWithBuckets(pool, instrumentID)` — the newest daily rows plus the buckets, one place,
  no other query changing.
- Wire the decision's gather to use it when buckets exist; otherwise it passes today's rows.

**Acceptance:** `ComputeIndicators` on a dense 300-session series and `ComputeIndicatorsFrom` on
(70 newest daily + 13-session buckets of the rest) return the same 200-day mean and 52-week range
within `1e-9`, and the same RSI14/ATR14 within 1% (Wilder smoothing cannot see the folded past). `ComputeIndicators`
alone keeps every existing test green. Nothing writes `bucket` rows yet, so behaviour on a real
database is unchanged.

## Slice 2 — the writer, and the migration that converts in place

Branch `feat/bar-tiers-writer`.

- `store.WriteBuckets(pool, instrumentID, buckets)` and the daily refresh path that produces them
  from the fetched year.
- A one-time conversion, keyed on a settings marker, that for each instrument: keeps 70 daily rows,
  collapses the rest into 13-session buckets, deletes the collapsed rows, and cuts intraday to the
  newest 10 days. Idempotent.
- `store.PruneBars(pool, now)` beside `PruneNews`: 70 daily, 20 buckets. There is no intraday
  retention because no intraday row is stored.

**Acceptance:** with a seeded dense series, the conversion leaves 70 daily + 20 buckets and the
six indicators are unchanged before and after; a second run changes nothing. `PruneBars` deletes
exactly the rows past each horizon and nothing else.

## Slice 3 — fetch only what is needed

Branch `feat/bar-tiers-fetch`.

- `market.Between(symbol, interval, from, to)` using the existing `period1`/`period2` builder.
- Poll uses `15m` from today's session open to now, not `5d` — the tape is transient either way.
- The year's `1d` series already fetches once per IST day; it now also feeds the buckets.

**Acceptance:** a fake transport asserts the exact query window (session open for the tape, one
year for the daily series) and that a poll writes no intraday row.

## Slice 4 — the chart's data endpoint

Branch `feat/bar-tiers-chart`.

- `GET /api/instruments/:symbol/chart?range=1d|1w|1m|3m|6m|1y&from=&to=`: a day or a week comes
  live from the exchange and is never stored; a month and three months read the daily rows; six
  months and a year read the buckets (falling back to daily before any bucket exists). A custom
  window goes live at the interval its span deserves.
- No new storage; no change to the analysis payload.

**Acceptance:** each stored range returns the expected resolution and row cap, a bad custom range
says so, and the live windows are pinned in `market`.

## Slice 5 — the control

Branch `feat/bar-tiers-chart-ui`.

- `api.chart`, a `bars` override on `PriceChart.vue`, and a range control (1D · 1W · 1M · 3M · 6M ·
  1Y · Custom) on the instrument page.

**Acceptance:** screenshots at 1440 and 390, light and dark, with `getBoundingClientRect()` on the
control row; switching a range refetches and the chart redraws.
